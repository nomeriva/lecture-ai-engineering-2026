## 宿題

- 取り組んだレベル：基礎
- やったこと：`app/config.py` の `RAG_TOP_K` を `5` から `3` に変更した。
- 比較した質問と、固定した条件：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか ？ QLoRAは何を加えますか？」。使用モデルは `gemini-3.5-flash-lite`。変更前後でモデルと質問は同じ。

### 変更前後の比較結果

| 項目 | 変更前（`RAG_TOP_K = 5`） | 変更後（`RAG_TOP_K = 3`） |
|---|---|---|
| 回答 | 正答。元の重みを固定し、低ランクの差分を学習。QLoRAでは4bit量子化を追加 | 正答。説明は変更前と同様 |
| LLMが回答中に提示した参照先 | 第2回 PDF p.51、p.52 | 第2回 PDF p.51、p.52 |
| `search_materials` の呼び出し | 1回 | 1回 |
| 検索語 | `LoRA QLoRA 固定 学習` | `LoRA 固定 QLoRA` |
| 時間 | 3.40秒 | 8.03秒 |
| 入力トークン | 3,027 tokens | 2,077 tokens |
| 出力トークン | 192 tokens | 232 tokens |
| モデル応答回数 | 2回 | 2回 |
| 生成API推定費用 | $0.001388 | $0.001203 |

- 考察：入力トークンは約31.4%削減され、生成API推定費用は約13.3%削減された。回答内容は両条件とも妥当であり、LLMが提示した参照ページも同じだった。一方、所要時間は4.63秒増加した。ただし、参照先の本文との照合は未実施である。モデルが生成した検索語も異なるため、この単発実験だけで性能差を断定できない。検索件数は上限設定であり、実際の取得件数を確認したとは断定できない。
- 別の質問での検証、再現性の確認：未実施
- 気づき・疑問：検索件数の上限を減らすことで入力トークンと推定費用は減少したが、応答時間は増加した。単発の結果であり、他の質問や複数回の実行で追加検証が必要。
